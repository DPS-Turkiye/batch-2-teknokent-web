# Internationalization

The app uses [next-intl](https://next-intl.dev). Turkish is the primary language; English is behind the
`NEXT_PUBLIC_ENABLE_ENGLISH` flag until the main screens are translated.

## Message catalogs

| File                                      | Contents                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `src/messages/tr.json`                    | The source of truth. Every key the app uses.                                                   |
| `src/messages/en.json`                    | The same keys in English.                                                                      |
| `src/messages/profile-tools/{tr,en}.json` | The `profileTools` namespace, merged in by `src/i18n/request.ts`.                              |
| `src/messages/odtu/{tr,en}.json`          | The ODTÜ overlay: only the texts that differ for ODTÜ accounts (student and academic wording). |

Rules:

- **No hardcoded UI text.** Every string a user can see, including `aria-label`, placeholders, toast messages and
  validation errors, is a message key. Code and comments are in English; UI copy is written in Turkish first.
- **Keys are typed.** `src/i18n/next-intl.d.ts` types `Messages` from `tr.json`, so `t("missing.key")` is a type error,
  in `src` and in tests.
- **English has every Turkish key.** `test/messages.test.ts` fails when `en.json` misses a key, a list item, or an ICU
  placeholder that Turkish has.
- **The ODTÜ overlay is sparse.** Add a key there only when ODTÜ wording differs. `mergeMessages`
  (`src/lib/account-type.ts`) lays it over the base key by key; a list in the overlay replaces the base list whole.
- Group keys by screen or feature (`programWeekPlan.add`, `mentorProfile.saved`); reuse a namespace's keys instead of
  adding near-duplicates.
- Use ICU arguments and plurals (`{count, plural, one {…} other {…}}`) instead of concatenating strings.

## Reading messages

| Where                                | How                                                                                                       |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Client components and hooks          | `const t = useTranslations("namespace")`                                                                  |
| Server components                    | `const t = await getTranslations("namespace")`                                                            |
| Route handlers (error messages)      | `await apiText("key")` from `src/lib/server/api-response.ts` (namespace `apiErrors`)                      |
| Plain modules that cannot call hooks | `clientText("key")` from `src/i18n/client-texts.ts` (namespace `clientErrors`), set up by the root layout |

Enum values shown to users are translated through a key per value, for example
``t(`programStatus.${status}`)`` with `status` typed as `ProgramStatus`, so a missing translation is a type error.

## Locale

`resolveLocale` (`src/lib/i18n.ts`) picks the saved choice from the `LOCALE_COOKIE`, then the browser's language, and
falls back to Turkish. Without `NEXT_PUBLIC_ENABLE_ENGLISH=true` it always answers Turkish. The backend receives the
locale as `Accept-Language`, so its error and field messages come back in the same language.

## Formatting

- Dates and times: the helpers in `src/lib/utils.ts` and `src/lib/format.ts`, given the active locale. Do not call
  `toLocaleDateString` with ad hoc options in components.
- Case conversion of Turkish text uses the locale: `text.toLocaleLowerCase("tr")` (so `I` becomes `ı`).
- Text saved to the backend for another person to read (for example an automatic accept message) stays Turkish, like
  other saved texts; these live as constants with a comment.
